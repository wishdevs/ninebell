0. 대전제 — 왜 이 자동화는 어려운가

일반 웹 스크레이핑/E2E와 무엇이 다른지부터 공유해야, 아래의 모든 규율이 왜 존재하는지 이해됩니다.

  • 그리드가 DOM이 아니라 <canvas>다. 상용 RealGrid + 더존 DEWS 래퍼가 셀을 캔버스에 그린다. Playwright locator·텍스트 셀렉터·DOM 스냅샷이 전부 무효이고, 셀에 접근할 표준 수단이 없다. → 페이지 안의 그리드 JS 인스턴스를 잡아 API로 조작하는 것이 유일한 경로다.
  • 화면이 "입력 폼"이 아니라 "업무 규칙 실행기"다. 셀 하나를 채우면 검증 팝업이 뜨고, 연쇄 계산이 돌고, 회계 분개 상태가 만들어진다. 값만 주입하면 겉보기에 채워졌지만 서버 상태가 미완이 되어 저장이 불투명한 에러로 거부된다 (§4 setValue 함정).
  • 일부 동작은 되돌릴 수 없다. 저장(F7)은 실제 회계 전표를 만들고, 상신(결재)은 회수 수단이 제한적이며, 회계전표 화면에는 삭제 기능 자체가 없다. 테스트 한 번의 실수가 실운영 데이터가 된다 → 모든 설계가 안전 경계를 중심으로 돈다.
  • 성공/실패 신호가 표준적이지 않다. 로그인에 성공해도 URL이 안 바뀌고, networkidle은 SPA 롱폴링 때문에 영원히 안 잡히고, 저장 "완료" 메시지 없이 팝업 하나로 거부된다. → 판정은 항상 요소/그리드 상태로 한다.
  • 타이밍이 이중으로 취약하다. 정상 경로를 빠르게 돌리려는 대기 축소와, 느린 세션에서 관찰창을 지키려는 대기 확대가 충돌한다. 이 프로젝트 간헐 실패의 최대 단일 원인이 이 축의 혼동이었다 (§6 시간축 규율).
핵심 태도

브라우저 자동화(API 아님)는 데이터를 가져오거나 조작하는 방법이 화면마다 조금씩 달라 한 번에 맞지 않는다. 그래서 이 문서의 모든 방법론은 하나로 수렴한다 — 추측하지 말고 실측으로 확정하고, 비가역 액션은 항상 게이트 뒤에 둔다.

1. 아키텍처 — 3계층과 두 개의 시간축

노하우가 코드 어디에 사는지가 곧 유지보수 전략입니다. "취약한 것은 한 곳에 모은다"가 제1원칙.

에러 설계

프리미티브(browser/*)는 실패를 False/None으로 돌려주고, 상위 계층(omnisol/patterns)이 그것을 도메인 오류로 승격한다: OmnisolError → AuthError(→LoginPageError) / UserTypeError / MenuError / GridError / PopupError. 이렇게 해야 최상위가 "자격증명 오류(401)"와 "인프라 실패(502)"를 구분해 사용자에게 읽을 수 있는 메시지로 분기한다.

1.2 Playwright 사용 방식

  • async API 전용 — LangGraph 노드가 코루틴이라 sync API는 애초에 불가.
  • 헤드리스가 기본, 헤디드는 디버깅 전용 — env 스위치(ERP_HEADLESS=0, e2e는 E2E_HEADLESS=0)로 전환. 자동화가 반복 실패하면 다음 실행은 헤디드로 재현하는 것이 규칙.
  • 페이지 소유권은 러너에 — 러너가 page를 만들어 그래프 state로 주입한다. 노드가 page를 만들면 수명 관리·스케일 래핑·크래시 복구가 흩어진다.
  • 좌표는 전부 요소 bbox 동적 계산 — 뷰포트를 키워도 빗나가지 않는 유일한 방법.
함정 — 뷰포트 폭

뷰포트는 1920×1200으로 확정(2026-08-14). 1440에서는 조회조건이 2줄로 접히고 그리드가 중간 컬럼에서 잘렸다(그리드 폭 1162 → 1642). "스크린샷이 깨져 보인다"는 리포트의 원인이 비율이 아니라 폭이었다. 별도 창(결재창)은 세로로 길어 1920×1500으로, 폭은 부모와 같게 강제 리사이즈한다 — 소형 창에서만 검증한 절대 좌표가 라이브에서만 터진 사고의 재발 방지다.

1.3 세션 관리

  • 자격증명 비저장 — 매 실행 1회 로그인 → 작업 → 즉시 폐기. 비밀번호는 DB에 저장하지 않고 RAM 캐시만.
  • 세션 워밍(storage_state RAM 캐시, TTL 30분) — 실측으로 같은 상태를 컨텍스트 3개가 동시에 써도 ERP가 세션을 끊지 않음을 확인한 뒤 도입. 콜드 33.3s → 웜 23.2s. 만료돼도 login 노드가 로그인 폼을 보면 정상 로그인하는 자가 치유 구조라 순수 최적화다. 단 디스크 저장은 금지(세션 토큰).
  • 같은 ERP 계정의 동시 실행 금지 — 세션이 서로를 밀어낸다. 로그인/실행 세마포어 분리, 동시 실행 상한 2.

1.4 두 개의 시간축 — 이 프로젝트에서 가장 중요한 설계

대기 시간을 다루는 축이 둘이고, 서로 직교하며, 절대 섞이면 안 된다.

delay_scale (_ScaledPage)latency.factor()
무엇정상 경로의 고정 sleep 축소실패/지연 시 폴링 상한 확대
구현page.wait_for_timeout만 배율 적용하는 프록시EMA(α=0.3), clamp 1.0~4.0 자동 학습
값에이전트별 0.15~0.4 (env 우선)확인 소요·그리드 출현 실소요로 자기갱신
적용 대상wait_for_timeout 전부관찰 상한(budget_ms/budget_polls)만
 
# runner.py — page 위임 프록시. wait_for_timeout 만 배율, 나머지는 원본 위임
class _ScaledPage:
    def __init__(self, page, scale):
        object.__setattr__(self, "_page", page)
        object.__setattr__(self, "_scale", scale)
    async def wait_for_timeout(self, ms):
        return await self._page.wait_for_timeout(max(0.0, ms * self._scale))
    def __getattr__(self, name):
        return getattr(self._page, name)
시간축 규율 — 간헐 실패의 최대 단일 원인

관찰 상한은 반드시 실시간(time.monotonic() + asyncio.sleep)이어야 한다. waited += interval + page.wait_for_timeout(interval) 형태의 명목 카운터를 쓰면 delay_scale 0.15에서 2.5초짜리 관찰창이 실제 ~375ms로 붕괴한다. "빈 그리드를 결과 0건으로 오판"류 사고 전부가 여기서 나왔다. 이 규율은 소스 레벨 린트 테스트(tests/test_time_axis_lint.py)로 강제한다 — 사람의 주의력에 맡기지 않는다.

한 줄 요약: "판정은 조건이, 시간은 예산". 성공 판정은 상태 조건(rowcount·요소 출현)이 하고, 시간은 그 조건을 기다리는 실시간 상한(예산)일 뿐이다. 2026-07-31 대기 체계 전면 개편에서 고정 sleep을 조건 폴링으로 대거 교체해 런당 4~12초를 단축했다 — 단, Kendo 정착·입력 리듬처럼 확실한 상태 신호가 없는 미세 대기는 의도적으로 남겼다. 전환은 신호가 있는 곳에서만.

2. 진입 플로우 — 로그인 · 사용자유형 · 메뉴

본 업무에 도달하기까지의 3단계. 여기서의 판정 실수는 이후 전 단계를 오염시킵니다.

2.1 로그인 — 성공 판정은 URL이 아니다

문제
옴니솔은 로그인에 성공해도 URL이 그대로일 수 있다. networkidle은 SPA 롱폴링/keepalive 때문에 거의 잡히지 않아 타임아웃 상한(12~20s)을 통째로 태운다.
해결
domcontentloaded까지만 기다린 뒤 요소 상태를 폴링한다. 콜드(로그인 폼 출현) vs 웜(아바타 출현)을 갈라서 판정하고, 제출 후에도 아바타 출현을 양성 신호로 폴링한다. 제출 후 상한이 소진됐는데 로그인 폼이 남아 있으면 자격증명 오류(AuthError), 폼도 대시보드도 없으면 인프라 오류(LoginPageError)로 구분해 던진다 — 이 구분이 없으면 서버 장애가 "비밀번호 오류 N회"로 집계되는 참사가 난다.
await page.goto(f"{base}/", wait_until="domcontentloaded", timeout=timeout_ms)
for i in range(latency.budget_polls(40)):          # 상한 ~12s (지연 배율 자동 확대)
    if await selector_present(page, selectors.LOGIN_USERID):
        break                                       # 로그인 폼 확인 → 콜드 경로
    if await selector_present(page, selectors.AVATAR) or await is_authenticated(page):
        return                                      # 웜 진입
    await page.wait_for_timeout(300)
else:
    raise LoginPageError("로그인 페이지가 로드되지 않았습니다(폼/대시보드 모두 미출현).")
await page.fill(selectors.LOGIN_USERID, userid)
await page.fill(selectors.LOGIN_PASSWORD, password)
await page.click(selectors.LOGIN_SUBMIT)
for i in range(latency.budget_polls(66)):          # 상한 ~20s
    await page.wait_for_timeout(300)
    if await selector_present(page, selectors.AVATAR):
        return                                      # 양성 신호: 아바타 출현
if not await is_authenticated(page, login_selector=selectors.LOGIN_USERID):
    raise AuthError("아이디 또는 비밀번호가 올바르지 않습니다.")
함정 — 계정별 편차

같은 코드가 계정 A에선 4.6초, 계정 B에선 25.3초 걸렸다(실측 2026-07-27). 원인은 ERP 측 계정 초기화면·권한 로딩으로 자동화가 줄일 수 없는 구간. 타임아웃을 "내 계정 기준"으로 잡으면 다른 계정에서 전멸한다.

2.2 아바타 셀렉터 — 콘텐츠가 아니라 구조로 잡는다

사고 (2026-07-27 라이브 장애)
img[src*=profile_circle]로 아바타를 찾았는데, 프로필 사진을 올린 계정은 src가 /download/image/<uuid>라 매칭이 아예 안 됐다. 아바타 클릭 타임아웃 → 사용자 패널 미개방 → 사용자유형 전환 실패로 연쇄.
해결
앵커의 클래스로 잡는다: a.user-pic. 사진 유무와 무관하게 동일하다. 태그(a)까지 고정하는 이유가 또 있다 — 열린 패널 안에도 div.user-pic(프로필 사진)이 있어, 태그를 안 박으면 패널 내부를 클릭해 패널이 토글로 닫힌다.
추가 함정
아바타 클릭은 토글이다. 앞 단계가 패널을 연 채로 남기면, 다음 단계의 "패널 열기"가 패널을 닫아버린다 (실측 2026-08-01: 이것 때문에 attempt 1이 통째로 날아갔다). 열기 전에 is_user_panel_open()을 확인해 idempotent하게 만든다.

사용자 패널 DOM (커스텀 레이어 — .k-window/[role=dialog] 아님)

.user-info.pop-over
├── .user-name .name        ← "이름 직책" 형태 ("석대현 프로")
├── .user-group .company    ← "(주)나인벨"
├── #ch_group               ← 사용자유형 select (옵션 가변!)
└── span.dept-name          ← 부서 ("인사/기획팀")
함정 — 부서명 정규식

부서 추출을 정규식 폴백으로 할 때 문자셋에 /를 반드시 포함할 것 — 없으면 "인사/기획팀"이 "기획팀"으로 잘린다(실제 버그였고, 부서 매칭 실패로 이어졌다).

2.3 사용자유형 전환 — JS 클릭은 핸들러를 깨우지 못한다

문제
옴니솔은 사용자유형(인사/회계/SCM)에 따라 접근 모듈이 다르다. 그런데 JS .click()이나 Kendo 위젯 .value()는 select 값만 바꿀 뿐 더존의 변경적용 핸들러를 깨우지 못한다 — 실제 컨텍스트(모듈 접근권)는 바뀌지 않는다.
해결
JS는 클릭할 좌표(bbox 중심)만 계산해 돌려주고, 실제 클릭은 page.mouse.click(trusted)으로 한다. 전체 시퀀스는 확인의 연속이다:
드롭다운 열기(좌표 실클릭)
  → 옵션 리스트 렌더 대기 — 좌표가 2회 연속 동일해야 진행
    (Kendo 열림 애니메이션 중 움직이는 li를 클릭하면 옆 항목을 짚는다)
  → 옵션 클릭 → 표시 반영 확인(폴링)

2.4 메뉴 진입 — 딥링크 + 그리드 개수 판정 + 권한팝업 즉시실패

패턴
사이드바를 더듬지 않고 딥링크(/FI/GLDDOC00300 등)로 직행한다. 도착 판정은 .dews-ui-grid 개수가 기대치 이상인가로 하고 (화면마다 그리드 수가 다르므로 메뉴 스키마에 기대값을 둔다), 동시에 매 폴마다 "메뉴를 찾을 수 없습니다/권한이 없습니다" 팝업을 검사해 즉시 실패한다.
가치
권한 없는 계정이 90초 타임아웃을 헛돌지 않고 3초 안에 "이 계정에 해당 모듈 권한이 없거나 메뉴가 이동/변경되었습니다"라는 읽을 수 있는 오류로 끝난다.
// MENU_CHECK_JS — 그리드 개수와 차단 팝업을 한 번에 스냅샷
() => {
  const grids = document.querySelectorAll('.dews-ui-grid').length;
  const dlg = [...document.querySelectorAll('.k-window, [role=dialog], .modal')]
                .find(x => x.offsetParent !== null);
  const popup = dlg ? (dlg.innerText || '').trim() : '';
  const notFound = /찾을 수 없|권한이 없|접근/.test(popup) && /메뉴|모듈/.test(popup);
  return { grids, notFound, popup: popup.replace(/\n+/g, ' ').slice(0, 50) };
}
복구 — 크래시 한정 1회 재시도

라이브에서 Page.goto: Page crashed로 런이 즉사했는데 2분 뒤 동일 경로가 1.2초에 정상 진입했다(2026-07-31). 재시도 1회만 있었어도 살았을 런이다. 이후 크래시 마커("Page crashed", "Target closed"…)에 한정해서만 같은 컨텍스트에 새 페이지를 만들어 1회 재시도한다. 교체된 page는 호출부로 반환해 전파하고 (배율 래퍼도 재래핑 — 교체로 배율이 유실되는 것을 방지), 일반 타임아웃·권한 오류는 재시도 없이 즉시 실패. "모든 실패에 재시도"가 아니라 "재시도가 의미 있는 실패 클래스에만"이 요점이다.

3. 팝업과 모달 — 처리 축이 3개다

"팝업을 닫는다"는 한 문장이 실제로는 세 가지 완전히 다른 메커니즘입니다. 축을 안 나누면 반드시 서로를 오탐합니다.

공지 레이어 팝업공지 시스템 팝업차단 확인 모달
정체같은 페이지의 .k-window 레이어window.open류 별도 Page같은 페이지의 .k-window
식별 앵커#close-today-chk 등 고유 idURL 마커(art_seq_no=…)제목·버튼 텍스트
처리체크+닫기, 실측 검증열린 창을 즉시 닫기'확인'/'예'만 클릭

3.1 공지 레이어 팝업 — 헤드리스에선 매번 뜬다

로그인 직후 ~1.5초 뒤 렌더되고 Kendo 백드롭이 화면 전체를 차단한다. "오늘 하루 보지 않기"의 영속이 브라우저 localStorage 단독이라, 매번 새 브라우저로 시작하는 헤드리스 세션에서는 항상 재현된다. 로그인 성공 직후, 아바타 클릭·메뉴 진입보다 먼저 닫아야 한다.

닫기도 검증한다(2026-07-23) — 종전에는 체크·닫기 클릭을 쏘고 끝(발사 후 미검증)이라 진입 애니메이션 중 좌표가 어긋나면 팝업이 남았다. 지금은 체크는 클릭 후 checked 실측으로 확정(빗나감 재시도 3회), 닫기는 클릭 직전 좌표 재평가 + 팝업 소멸 폴링으로 검증한다. 그리고 reload마다 다시 뜬다 — 사용자유형 전환 화면에서도.

함정 — 성능 최적화의 방향

진입 11.8초 중 5초 이상이 "공지 팝업을 기다리는 시간"이었다(2026-07-28 단계별 실측). 메뉴 도착 후 관찰창은 재출현이 없어 배경 감시로 전환해 런당 ~2.8초를 회수했다. 그런데 로그인 직후 대기까지 배경화했다가 되돌렸다 — 없애면 팝업 등장이 다음 단계(아바타 클릭)와 겹쳐 그 단계가 0.3s→2.4s로 늘어난다. 총합은 그대로인데 변동성만 커진다. 최적화는 실측 후에, 구간별로.

3.2 별도 창 팝업 — "어떻게 여는지"에 기대지 마라

일부 계정은 로그인 중 회사 홈페이지가 별도 브라우저 창으로 뜬다. 인페이지 다이얼로그 처리로는 절대 잡을 수 없어 축을 분리했다(PopupWatcher).

처음에는 window.open을 후킹해 공지 URL이면 열리지 않게 막으려 했다. 실패했다(2026-07-28 폐기) — 추적해 보니 공지창의 opener는 ERP 메인 페이지가 맞는데, 모든 프레임에서 window.open 호출이 0건이었다 (form target 등 다른 경로로 연다). 교훈: 열리는 메커니즘은 앱 내부 구현이라 언제든 다르고, "열린 창을 보고 즉시 닫는" 축은 메커니즘과 무관하게 동작한다. 관찰 가능한 결과에 기대라.

치명 함정 — 업무 창과 공지 창이 같은 호스트다

전자결재(EAP) 결제창과 공지창이 같은 호스트, 같은 경로다:

공지: uc.ninebell.co.kr/#/popup?art_seq_no=1573&…&callComp=UFAP013
결제: uc.ninebell.co.kr/#/popup?callComp=UBAP001&docID=…&approkey=…

"ERP 호스트가 아니면 닫는다"는 규칙은 결제창을 죽인다. 판정은 공지 마커 (art_seq_no=/callComp=UFAP)로 하고, 닫기 전 결재 마커(approkey=/callcomp=ubap…)를 한 번 더 검사한다. fail-safe 원칙: 공지로 확정되지 않으면 닫지 않는다 — 못 닫은 공지는 무해하지만, 업무 창을 닫으면 결재가 불가능해진다. 갓 열린 창은 about:blank라 목적지 URL이 정해질 때까지 잠깐 기다린 뒤 판정한다.

3.3 차단 확인 모달 — 지연 출현을 전제하라

카드팝업 '적용' 후 팝업이 닫힌 다음에 '예산현황' 모달이 떠서, 이미 다음 단계로 넘어간 코드가 TypeError로 죽었다(2026-07-02). 처리기(dismiss_blocking_modals)는 '확인'/'예' 계열만 클릭하고(취소/아니오 금지 — 진행 방향으로만), 첫 체크는 대기 없이 즉시, 이후 400ms 폴링, 2초 연속 조용하면 종료한다. 위험 액션 직전(저장 전 등)마다 이걸 한 번씩 돌리는 것이 지연 출현 모달에 대한 보험이다.

4. 캔버스 그리드 조작

이 프로젝트에서 가장 많은 피를 흘린 영역. RealGrid/DEWS는 캔버스에 그려지므로 표준 도구가 전부 무효입니다.

4.1 그리드 인스턴스를 잡는 법

DOM에 셀이 없으니, 페이지 안의 그리드 JS 인스턴스를 jQuery data로 잡아 API를 부른다.

$(".dews-ui-grid").eq(i).data("dewsControl")._grid                 // RealGrid GridView
$(".dews-ui-grid").eq(i).data("dewsControl")._grid.getDataSource() // DataProvider
  • 그리드 순서: [0]=마스터, [1]=디테일, [2]=항목. 팝업은 자체 그리드를 가진다.
  • 주력 API: getRowCount / getJsonRows / getValues / setCurrent / showEditor / checkRow / getCheckedRows / getColumns(fieldName·visible·editor 덤프용).
함정 — TreeGrid는 다른 위젯이다

.dews-ui-treegrid는 플랫 그리드와 별개 위젯이다(2026-08-13, BOM 화면). 범위형 getJsonRows(0, N-1)가 null을 반환하고(플랫 전용 API), for i in 1..rowCount 루프에서 ds.getLevel(i) + ds.getValue(i, f)로 한 행씩 읽는 것이 유일한 경로다. 인덱스도 다르다 — 1부터 count까지 포함(0은 숨은 루트).

4.2 off-by-one — getJsonRows는 end-inclusive

20행을 원하면 getJsonRows(0, 19)다. (0, 20)이면 21행이 되어 다음 문서의 행이 끼어든다 — 실측에서 실제로 다음 문서가 수집에 섞여 들어왔다. 해결은 관례가 아니라 구조다: 정규화 함수(normalize_range(start, count, total) → (start, end_inclusive, take))를 한 곳에만 두고, 모든 그리드 읽기가 그 래퍼(GridProvider.get_rows)를 지나게 한다. 호출자는 end-inclusive의 존재 자체를 몰라도 된다.

4.3 setValue는 #1 조용한 오염원이다

문제
grid.setValue(row, field, value)는 dataSource에 값을 쓰지만 ERP의 on-edit 핸들러를 발화시키지 않는다. 그 핸들러가 검증 팝업·연쇄 계산·회계 분개 상태를 만드는 자리다.
결과
행은 채워진 것처럼 보이는데 서버 상태가 미완 → 저장이 "데이터베이스 처리 중 오류" 같은 불투명한 에러로 거부되거나, 문서가 미묘하게 무효가 된다. 원인과 증상이 멀리 떨어져 있어 디버깅이 지옥이다.
실제 사례 (2026-07-09)
공급가액을 타이핑하면 ERP가 '예산현황' 확인 다이얼로그를 띄우고, 그걸 확인해야 예산집행+분개+합계가 채워진다. setValue는 이 다이얼로그를 건너뛰어 모든 저장이 DB 에러를 냈다. 며칠을 헤매다 실사용자의 한 마디가 뚫었다 — "금액을 입력하면 확인을 눌러야 하고, 이게 완료돼야 저장도 가능해요."
해결 — 실제 에디터에 타이핑하고, 커밋하고, 트리거된 팝업을 처리한다
# 1) 마지막 행의 셀 에디터 열기 (setCurrent + showEditor)
r = await page.evaluate(js_lib.OPEN_DETAIL_CELL_EDITOR_JS, "SPPRC_AMT2")
# 2) 진짜 오버레이 input 찾기 — width > 10 (…gridDetail_number).
#    width 1 짜리 …gridDetail_line 은 디코이 — 매칭하면 키가 엉뚱한 셀로 간다
inp = await page.evaluate(AMOUNT_EDITOR_INPUT_JS)
# 3) 클릭 → select_text → 순차 타이핑 → Tab
loc = page.locator(f'input[id="{inp["id"]}"]')
await loc.click()
await loc.select_text()            # ⚠ Meta+A 금지(에디터가 닫힌다),
                                   # ⚠ macOS Ctrl+A 는 line-start(12500 이 125000 이 된다)
await loc.press_sequentially("5000")
await loc.press("Tab")             # ⚠ Enter 아님 — blur/change 가 핸들러를 더 확실히 깨운다
# 4) 트리거된 '예산현황' 다이얼로그 확인
await dismiss_blocking_modals(page)
# 5) 검증 — 값 반영 + 의존 필드 자동채움(← 핸들러가 발화했다는 증거)
vals = await page.evaluate(READ_AMT_JS)
규칙
필드 입력이 무언가(팝업·재계산·연동필드)를 트리거해야 하는 자리라면 반드시 타이핑한다. setValue는 on-change 동작이 없는 무기력 필드에만 안전하다. 이 구분은 플로우 명세 표기법에서 [값설정]과 [직접입력]이라는 서로 다른 동사로 박제했다 — 표기 단계에서부터 다른 행위임이 보이게. 참고로 문서종류별 편차도 있다: 세금계산서 화면은 같은 공급가액 타이핑에 다이얼로그 없이 즉시 세액 10%가 자동계산됐다. 화면마다 실측하라.

4.4 숨은 backing 필드 ≠ 보이는 위젯

dataSource에는 존재하지만 visible: false인 숨은 backing 필드가 있다. 여기에 값을 쓰면 코드는 영속되는데 사용자가 보는 화면은 계속 빈칸이다. 실제로 상대계정거래처를 숨은 BFC_PARTNER_CD로 "세팅"했다가 사용자에게 "입력이 안 된 채 끝났다"는 판정을 받았다 — 실제 UI는 화면 하단의 별도 서브테이블(행마다 🔍 코드피커)이었다.

  • 검증은 dataSource가 아니라 표시값으로: getJsonRows(저장값) vs getDisplayValuesOfRow(렌더값) 대조. "코드는 저장됐는데 이름이 안 보이면" = 숨은 필드의 고전적 신호.
  • 반대 사례도 있다: 어떤 필드(FEOTH_ACCT, 상대계정)는 저장 시 자동 파생되며 편집 위젯 자체가 없다. 채우려는 모든 시도는 실패한다 — 3개 경로를 전부 실측 반증하고서야 확정했다(2026-08-19).

4.5 셀 에디터의 대상 행 — "항상 마지막 행"

F3(행 추가)로 만든 신규 행은 맨 아래에 추가된다. 에디터를 itemIndex 0 고정으로 열던 시절, 2패스 플로우에서 기존 행의 증빙유형을 열어 값을 덮어쓰는 실전 사고가 났다(2026-07-02). 판정 로직도 0행 고정이라 성공을 실패로 오판하는 이중 사고였다. 대상·판정 모두 getRowCount()-1을 참조한다.

4.6 상세(디테일) 로딩은 trusted 키보드에만 반응한다

문제
마스터-디테일 그리드에서 마스터 행을 옮겨 디테일을 로드하려 할 때, JS setCurrent()도 좌표 클릭도 디테일 로딩을 트리거하지 않는다. 로드 핸들러는 실제 키보드 입력(trusted)에만 반응한다. 게다가 앱이 디테일을 캐시해서(한 번 본 행은 재요청 안 함) 페이지 리로드로도 초기화할 수 없다.
검증된 루프
첫 행을 실클릭(포커스+행0 로드)한 뒤, 행마다 [디테일 읽기 → 실제 ArrowDown]을 반복한다. 누락 시 jiggle(ArrowUp→ArrowDown)로 재앵커링해 재로딩을 유도한다.
함정
jiggle이 최상단(행0)에서 돌면 ArrowUp은 무효인데 ArrowDown은 실동작해 커서가 행1로 밀리고, 이후 전체 수집이 한 행씩 밀린다 — 조인 키가 없는 그리드에서는 무증상 오염이다. jiggle 후에는 명시적으로 setCurrent를 다시 잡는다.

① 식별 필드 조인 — 디테일 첫 행의 마스터 키가 기대값과 일치할 때만 확정. 불일치는 직전 행의 디테일이 남은 것이므로 그 rows는 절대 돌려주지 않는다. ② 조인 키가 없으면 rowcount 변화 관측 후 2회 연속 동일. 상한이 소진되면 해당 행을 unverified: True로 명시 마킹해 올린다 — 조용한 빈값 금지.

4.7 수집 전략 2종 — 병렬 AJAX vs 키보드

  • 방법 A — 병렬 AJAX (권장, ~150ms/20행): 마스터는 getJsonRows로 즉시 일괄, 디테일은 앱 dataSource의 transport URL로 페이지 안에서 $.ajax를 병렬 발사한다. 앱의 전역 ajax 설정이 인증 헤더(JWT)를 자동 주입하므로 401이 없다 — 네트워크 가로채기도, fetch 위조도 아니다. 앱이 자기 서버에 하는 요청을 앱의 클라이언트로 대신 하는 것이 요점.
  • 방법 B — 키보드 폴백 (견고): §4.6의 trusted 키보드 순회. 캐시·서명·가로채기와 무관해서 항상 동작한다.
  • AUTO: A 시도 → 실패 시 B 폴백.

4.9 인덱스 공간 함정 — 10행을 의도했는데 99행이 체크됐다

2연타 사고 (2026-08-13 / 08-26)

① grid.getValue(i, f)는 ds.getLevel(i)보다 한 행 앞선 데이터를 돌려준다 — 이 조합으로 읽으면 전체 매핑이 한 행씩 밀린 오독이 생긴다. 필드는 반드시 ds.getValue(i, f)로.

② 체크 API에는 인덱스 공간이 둘이다: 데이터 행 공간(checkRow/getCheckedRows)과 아이템 공간(checkItem/getCheckedItems). ds로 계산한 자손 행 10개를 checkItem에 넘기자 99행이 체크됐다 — 다음 묶음과 그 하위 전체가 딸려왔다. API 종류가 아니라 인덱스 공간의 문제였다. 리더가 ds 공간이면 체크도 checkRow로 통일한다.

저장까지 갔다면 의도한 것과 다른 데이터가 섞인 문서가 생성됐을 것이고, 화면상 그럴듯해 사후 추적이 매우 어려웠을 것이다. 저장 게이트를 닫아둔 덕에 잡혔다 — 게이트의 존재 이유가 이것이다.

4.10 오버레이가 클릭을 삼킨다 — elementFromPoint가 심판

빈 행 삭제 클릭이 1차는 실패하고 2차에 성공하는 간헐 증상이 있었다. 처음엔 타이밍 문제로 진단하고 재시도를 넣었는데 그 진단이 틀렸다(2026-08-01). 진짜 원인: 셀 에디터가 열리면 DEWS가 상단 버튼영역을 .disabled-main-top-area 오버레이로 덮어, 삭제 버튼 좌표 클릭이 오버레이에 흡수된다. 좌표·rect는 동일한데 elementFromPoint 결과만 오버레이→버튼으로 바뀌는 것이 결정적 증거였다. 1차 클릭의 유일한 효과가 오버레이 해제라서 2차가 100% 성공했던 것.

수정: 클릭 전 게이트 — Escape로 에디터 정리 → elementFromPoint가 실제 버튼이고 현재행이 빈 행일 때만 클릭. 3/3 1차 성공으로 바뀌고 런이 150s→127s로 줄었다. "재시도로 덮이는 간헐 실패"는 대부분 원인이 따로 있다.

4.11 같은 라벨의 버튼이 6개일 때 — id로만

구매발주 화면에는 [적용] 버튼이 6개 있는데, 같은 컨테이너를 공유해 closest('tr')류의 rowText로는 6개가 전부 동일하게 보인다 — 라벨 키워드 매칭은 항상 첫 번째(엉뚱한 필터)를 집는다. 각 버튼의 고유 id(b_public_sl_cd, btn_bfdedt_dt…)를 실측해 표로 박아두고 id로만 클릭한다. "텍스트로 요소 찾기"는 엔터프라이즈 화면에서 기본값이 될 수 없다.

4.12 날짜 문자열 함정 모음

  • ERP 날짜 문자열은 KST 자정을 UTC로 표기한다: 2026-08-14 → '2026-08-13 15:00:00+00:00'. 앞 10자만 자르면 하루 밀린다 — +09:00 환산 헬퍼를 거친다.
  • 회계일자 세팅은 compact 'YYYYMMDD'만 — 대시 포함 'YYYY-MM-DD'는 오류 없이 셀을 비운다(실측).
  • 삭제 가드에서 날짜 매칭을 쓰지 않는다 — UTC 저장 + 회계일이 기간 말일이라 로컬 '오늘'과 어긋나 오판한다. 신원 판정(작성자·구분·미결)으로 교체했다.
  • 조회 기간은 항상 명시 세팅 — 화면 기본값이 "1일~오늘"인 화면과 "1일~말일"로 세팅하는 화면이 섞이면 두 화면의 조회 결과가 어긋난다(두 화면을 함께 쓰는 플로우에서 실사고).
  • 날짜 위젯은 캔버스 렌더 + 1×1 디코이 input — 달력 클릭 경로는 포기하고 그리드 API로 대체했다.

5. 코드피커 — 팝업 왕복의 규율

5.1 이름 매칭 — 무매칭 시 임의 선택 금지

공용 엔진(fill_codepicker)의 핵심 규율은 하나다: 확신 없이 아무 행이나 고르지 않는다.

keyword 있음 → 이름에 keyword 포함하는 후보만
  ├ 유니크 코드 1개로 수렴 → 선택
  ├ 이름 완전일치가 단일 코드로 수렴 → 그것 선택
  │   (실전: 'SPARES_ACM' 이 'SPARES_ACM KOREA' 에도 포함돼 모호 실패하던 문제)

5.3 "적용" 버튼의 3중 함정

  • 적용이 안 먹는 팝업이 있다 — 일부 서브디테일 피커는 행 선택+적용 클릭이 아무것도 커밋하지 않고 팬텀 빈 행만 추가한다. 실제로 먹히는 제스처는 결과 행 더블클릭(RealGrid apply-on-dblclick)이었다. 행 좌표는 팝업 그리드의 getBoundingClientRect로 계산한다(헤더 ≈30px + rowIndex×≈32px) — getCellRect는 팝업 밖 좌표를 돌려줬으므로 신뢰 금지.
  • 부분일치가 엉뚱한 버튼을 집는다 — 버튼열이 ['품목정보','조회','일괄적용','적용','닫기']일 때 부분일치 첫 버튼 검색은 '일괄적용'을 집는다(2026-08-24). '적용'은 창 스코프 정확일치로만.
  • 적용이 읽는 선택과 우리가 만든 선택이 다르다 — 어떤 팝업의 '적용'은 체크박스 열만 읽는다. setCurrent/setSelection(하이라이트)은 무시되어 "선택한 내역이 없습니다"로 거부된다(2026-08-24). grid.checkItem(i, true) → getCheckedRows 재독으로 넣어야 한다.

5.4 적용·닫힘도 검증한다 — 그리고 실패 정리 규율

예전 코드는 적용 버튼이 안 나타나도 {ok: True}를 돌려줬다 — 선택이 폼에 안 붙었는데 "반영됨"으로 기록되는 조용한 가짜 성공. 지금은 버튼 출현 폴링 → 클릭 → 팝업 닫힘 폴링을 모두 통과해야 성공이다.

스테일 피커 — 다음 왕복을 오염시킨다

실패 경로에서 피커를 안 닫고 반환하면, 다음 fill_codepicker가 남은 팝업을 자기 것으로 오독해 이전 그리드에서 선택/적용한다(2026-07-24, 08-07 동형 사고 2회). 실패 시 반드시 닫고, 닫혔는지까지 확인하고, 첫 닫기가 빗나갔으면 재닫기한다. 그래도 안 닫히면 실패 사유에 "다음 피커 오독 위험"을 명시해 반환한다.

async def _fail(reason: str, **extra) -> dict:
    await page.evaluate(js_lib.PICKER_CLOSE_JS)
    if not await _wait_picker_closed(page):
        await page.evaluate(js_lib.PICKER_CLOSE_JS)      # reapply
        if not await _wait_picker_closed(page):
            reason = f"{reason} / ⚠ 실패 정리 중 피커 미닫힘(다음 피커 오독 위험)"
    return {"ok": False, "reason": reason, **extra}

5.5 rowcount 안정화 — 0행은 조기 안정이 아니다

검색(Enter) 직후 그리드는 잠깐 비었다가 서버 재조회 결과로 채워진다. 이 순간을 "결과 0건"으로 오판해 40행 전량이 "후보 0건"으로 실패한 실전 회귀가 있었다(2026-07-04). 안정화 폴링의 세 가지 규율:

async def _wait_picker_rows_stable(page, *, cap_ms=3_000, interval_ms=200, min_ms=0) -> int:
    """피커 그리드 rowcount 가 준비되고 2회 연속 동일해질 때까지 폴링.
    min_ms: 안정 판정의 두 관측이 모두 이 시간 이후여야 한다 — 검색 직후
    '옛 rowcount 의 안정'을 새 결과로 오인하는 것을 방지."""
    prev, prev_elapsed, last = None, 0.0, -1
    t0 = time.monotonic()
    while (time.monotonic() - t0) * 1000 < cap_ms:   # ⚠ 상한은 실시간 — delay_scale 무관
        await page.wait_for_timeout(interval_ms)      # 폴 간격만 스케일된다
        n = await page.evaluate(js_lib.PICKER_ROWCOUNT_JS)
        elapsed = (time.monotonic() - t0) * 1000
        if isinstance(n, int) and n >= 0:
            last = n
            if n > 0 and n == prev and prev_elapsed >= min_ms:   # ⚠ 0행은 조기 안정 불인정
                return n
            prev, prev_elapsed = n, elapsed
        else:
            prev, prev_elapsed = None, 0.0
    return last          # 진짜 0건 검색은 cap 소진 후 0 을 반환한다
  1. 상한은 실시간(monotonic) — 배율에 붕괴하지 않는다. 폴 간격만 스케일.
  2. 0행은 조기 안정으로 인정하지 않는다 — 진짜 0건은 상한 소진 후에만 확정.
  3. min_ms — 검색 전 rowcount가 그대로 "안정"으로 잡히는 것을 막는다.

5.6 요소 출현 폴링 — 환경 편차의 보험

개발 환경에서 완벽하던 코드가 프로덕션(컨테이너)에서만 "프로젝트 후보 0건"을 냈다(2026-07-10). 원인: 피커 버튼이 컨테이너의 느린 렌더 + 잔여 모달 때문에 ~0.5초 늦게 나타나는데, 버튼 bbox가 없으면 즉시 False를 반환하던 코드가 그 전에 실패했다. 버튼 출현 폴링(최대 6s)을 넣자 프로젝트 덤프가 0→2,422건. 헤드리스 DOM 조작에서 "요소가 지금 없음 = 실패"는 성급하다 — 출현 폴링이 기본값이어야 한다. 부작용 행(등록이 덧붙이는 빈 디테일 행)은 감지(행수 +1 = 성공 신호) 후 ERP 네이티브 방식(행 선택 → 툴바 삭제)으로 지운다 — dataSource.removeRow는 고아 상태를 남겨 저장이 DB 에러를 낸다.

5.7 검색어 주입도 실타이핑으로

검색어를 JS로 주입하면 팝업이 소멸하는 실패 모드가 "간헐"처럼 보였는데, 매트릭스 프로브로 재현하니 주입 방식의 결정적 갈림길이었다(2026-08-28, 2회 반복 완전 일치). 현재 구현은 실타이핑 (오픈 직후의 포커스+전체선택 상태 이용, 값 검증 실패 시 트리플클릭 폴백)이다. 또 검색어에 # 문자가 들어가면 별도의 실패 모드가 난다 — 금지 문자로 처리.

6. 검증 커널과 대기 전략

조용한 실패의 대부분은 "클릭 호출이 성공했다"를 "값이 반영됐다"로 착각하는 데서 나옵니다. 그래서 확인(confirm)을 일급 프리미티브로 만들었습니다.

6.1 "세팅했으면 반영을 확인하고 넘어간다"

피커 '적용'이 폼에 안 붙고, 드롭다운이 change 핸들러에 되돌려지고, 조회를 눌렀는데 그리드가 아직 이전 결과이고, 탭이 안 열렸는데 그 화면을 조작하는 — 이 모든 사고의 공통 처방이 독립 리더에 의한 재확인이다. 확인 커널(verify.py)은 이를 3축으로 분류한다.

축 1 — 무엇을 읽어 확인하나 (kind)

셀렉트 선택값 / 피커 표시값 / 팝업 개폐 수 / 그리드 행수 / 화면·탭 도착(보이는 라벨) / 화면 텍스트 — 종류별 리더 JS를 공용 라이브러리에 둔다. 액션을 수행한 코드가 스스로 성공을 판정하지 않는다(자기충족 readback 금지).

축 2 — 언제 반영되나 (timing)

INSTANT = (0, 120, 360, 900)      # native select, input readback (DOM 즉시)
ASYNC   = (0, 300, 900, 2_400)    # 피커 적용 표시값, 팝업 개폐 (위젯 왕복)
HEAVY   = (0, 600, 1_800, 4_500)  # 화면·탭 전환, 조회 결과 그리드 (서버 왕복)

즉시 1회 + 실패 시 점증 대기 3회. 정상 경로는 첫 read(0ms)에서 끝나므로 추가 지연이 0이다. 대기는 실시간(asyncio.sleep) — page.wait_for_timeout을 쓰면 배율에 줄어들어 느린 세션에서 확인이 조기 실패한다. 점증 대기에만 지연 배율이 곱해진다.

축 3 — 다른 값에 영향을 주나 (cascade)

  • settle= — 매 read 직전 정착 대기(로딩 오버레이 소멸 등). 로딩 중 스냅샷이나 직전 조회 결과(스테일)를 읽는 것을 막는다.
  • reapply= — 재시도 때 액션 재실행. 기다린다고 붙지 않는 값(핸들러가 되돌리는 드롭다운 등) 전용.
  • A가 B를 바꾸면 A 확인 후 B를 다시 확인한다.
# "실행 → 확인" 한 줄 조립
res = await verify.apply_confirm(
    apply=lambda: steps.set_docu_types(page, ["국내매출", "해외매출"]),
    verify=partial(verify.confirm_display, page, "전표유형"),
    contains="국내매출",
    retry_apply=True,          # 되돌려지는 값 → 재시도마다 재실행
    timing=verify.ASYNC,
)
if res.mismatch:   # 확인은 됐는데 값이 다름 → 하드 실패
    return {"ok": False, "reason": res.reason}
if res.unknown:    # 리더가 못 읽음 → 경고 후 진행
    logger.warning("전표유형 확인 불가 — 진행: %s", res.reason)
실패 처리 정책 — "값이 다르면 중단, 읽지 못하면 경고"

불일치(mismatch)는 하드 실패로 중단하고, 확인 불가(unknown)는 경고 후 진행한다. 리더가 화면을 못 읽는 것은 오탐일 수 있어 멀쩡한 실행을 끊는 근거로 쓰지 않는다 — 다만 조용히 넘기지도 않는다. 확인하지 못한 채 지나갔다는 사실이 로그에 남아야, 나중에 "완료로 보이는데 값이 안 붙은" 결과를 되짚을 수 있다. 하드/소프트의 경계는 "그 값이 처리 대상 집합을 정의하는가"로 가른다 — 전표유형·조회 기간처럼 대상을 정의하는 값은 하드, 범위 보조 값은 소프트.

함정 — 도착 앵커로 native select 금지

Kendo DropDownList는 원본 <select>를 display:none으로 숨기고 위젯을 대신 그린다. 화면 도착 확인의 앵커로 native select의 가시성을 쓰면 올바른 화면에서도 영원히 실패한다(2026-07-27 라이브 실패로 확정). 반면 값 세팅·읽기는 jQuery 위젯 API라 숨은 select에서도 정상 동작한다 — 가시성 앵커로만 부적합한 것. 도착 앵커는 조회조건 라벨처럼 눈에 보이는 것으로 잡는다. 또 하나: 다중 메뉴 탭 화면에서는 다른 탭의 DOM이 그대로 남아 있으므로 '존재'가 아니라 '가시성'으로 판정한다 — 안 그러면 엉뚱한 탭을 조작한다.

6.2 시간 스케일링 취약성 — 프로덕션 조건으로 검증하라

배율 1.0에서 튜닝한 고정 대기는 0.4에서 전부 짧아져 flake가 된다(실제로 빈행 삭제가 실패했다). 해결은 §1.4의 반복이다: 고정 settle → 조건 폴링. 그리고 검증할 때 프로덕션과 같은 배율 프록시로 page를 감싼다 — raw 1.0에서 통과한 프로브는 프로덕션의 실패를 재현하지 못한다. 2026-08-07 감사에서는 반대 사례도 나왔다: 명목 카운터 붕괴 때문에, 막으려던 프로덕션 사고가 특정 에이전트(배율 0.15)에서만 재현 가능한 상태였다.

흥미로운 실측 하나(2026-08-26): 압축 실행(0.4)에서 다이얼로그 처리 직후의 첫 조회가 반영되지 않고 2회차에 반영됐다(try1 164행 → try2 664행). 헤디드 실시간(1.0)에서는 1회로 됐다 — 즉 "조회 2회"는 ERP 요구사항이 아니라 타이밍 아티팩트다. 횟수를 고정하지 말고 기대 행수 도달까지 재시도하고, 끝내 실패하면 명시적으로 실패시켜라 — 이 누락 때문에 이후 단계 전부가 잘못된 데이터셋 위에서 돈 사고가 있었다.

7. 안전 경계 — 비가역 동사 다루기

ERP 자동화는 실수가 곧 실운영 데이터입니다. 안전은 "조심하자"가 아니라 코드 구조와 표기법으로 강제합니다.

7.1 절대 안전 규칙

  1. 저장(F7)은 게이트 뒤에만. 전용 save 노드에서 confirm=True일 때만 발화. 저장 버튼 셀렉터는 상수로 존재하되 "참조용 — 절대 클릭 금지" 주석과 함께 둔다.
  2. 상신(결재)은 원칙 금지. 예외는 결재취소→상신취소→삭제로 가역임을 프로브로 먼저 증명한 계열 하나뿐이며, 그 증명(가역성 프로브)이 사용자 승인의 근거였다.
  3. 쓰기 검증은 격리된 테스트 계정 + 작성→검증→삭제 사이클로만.
  4. 삭제는 3중 가드. 작성자 일치 + 문서구분 일치 + 미결(전표번호 없음). 하나라도 어긋나면 삭제하지 않고 중단·보고.
  5. 자격증명 비저장.
  6. 성공 판정은 URL이 아니라 요소/그리드 상태.
  7. 라이브 2~3회 실패하면 멈추고 도메인 전문가(실사용자)에게 묻는다.

7.3 부작용 등급 표기법 — 문서에서부터 안전을 강제

플로우 명세(FLOW.md)의 모든 스텝은 정해진 동사와 등급으로만 적는다. 산문 금지.

────  ────────    ─────────────        ──────────────────  ──────  ────
등급   동사        대상: 값              사후 확인            시점    실패처리

  • [값설정] vs [직접입력]을 나눈 이유는 §4.3. [코드선택]을 한 동사로 묶은 이유는 열기·검색·선택·적용·닫힘확인을 따로 적으면 닫힘 확인을 빠뜨리기 때문 — 실제로 그 자리에서 스테일 피커 사고가 났다.
  • 확정·발신 등급 줄에는 승인필요가 붙어야 한다. 예외는 없다.

7.4 삭제 수단이 없는 화면 — 다른 아키타입

문서를 만드는 화면(작성→저장→삭제 사이클 가능)과 달리, 회계전표 조회·승인 화면은 전표를 만들지 않는다. 그리고 ERP에 회계전표를 삭제하는 로직 자체가 없다 — 만들면 되돌릴 수단이 없다. 이 계열은:

  • 플로우 명세에 확정/발신 등급 동사가 0줄이다. 스모크 테스트의 역할은 "게이트가 실제로 닫힌 채 종단 완주하는지 관찰"이며, 게이트를 여는 인자를 넘기지 않는다.
  • 날짜 필드를 추정해서 대상 그룹핑하지 않는다 — 결과 그리드의 어떤 날짜 필드도 조회 필터와 일치하지 않음을 실측했다. "하루로 좁혔다"고 믿고 대량 처리한 회귀(1건인 줄 알고 11건 처리)가 실제로 났다.
  • 대상 건수를 제한할 노브가 폼에 없으면, 실행 전 읽기 전용 조회로 기간을 이분 탐색해 대상 1~3건짜리 부분기간을 실측으로 찾아 넣는다. 못 찾으면 실행하지 않는다.

7.5 런 전역 시간예산과 저장 보호

워치독이 활동 시간(사용자 개입 대기 제외) 20분을 넘기면 스크린샷을 남기고 런을 종료한다. 단 이 취소가 저장 확정 구간 한가운데를 자르면 반저장이 되므로, F7 확정 구간은 shield로 감싼다 — 취소 신호를 흡수하며 저장 판정 완료 후 취소에 응한다(상한 30초). 인프라 측 종료 유예(컨테이너 stopTimeout)도 그보다 길게 잡아야 한다.

8. 방법론 — 녹화에서 운영까지

"코드부터 짜지 않는다"가 이 프로젝트의 SOP입니다. 불확실성을 단계별 게이트로 가둬, 추측이 아니라 실측으로 확정합니다.

8.1 9단계 게이트 개관

  1. 실현가능성 게이트 — 대상 화면(딥링크·사용자유형), 격리 테스트 계정, 사람이 하는 순서. 셋 중 없는 게 있으면 먼저 묻는다. STOP 조건: 2FA/CAPTCHA 존재, 격리 계정 없음, 대상 액션이 비가역인데 삭제 경로가 없음.
  2. 텍스트 플로우 + codegen 녹화 → 플로우 명세(PROCESS.md) 초안 — 핵심 단계, 아래 상술.
  3. 읽기 경로 검증(부작용 0) — 녹화가 확정 못 한 것(❓)만 헤드리스로 실측.
  4. 쓰기 경로 검증 — 격리 계정에서 게이트를 연 1회 실저장 → 무엇이 영속되는지 확인 → 즉시 삭제.
  5. 자가수정 루프 — 아래 8.3.
  6. 테스트 스위트 + E2E 사이클 — 아래 8.4.
  7. 그래프(워크플로우) 통합 — 확정된 방법을 단일소스 프리미티브로 옮기고 조립.
  8. 반복 검증 — 10회 실저장 사이클로 flakiness 측정(PASS/N · 평균 소요 · 잔존 0).
  9. 운영·모니터링 — 셀렉터 드리프트 런북.

8.2 Playwright codegen 녹화 — 사람의 한 번이 하루를 아낀다

새 화면 자동화의 입력은 둘이다: 업무 순서를 말로 받은 텍스트 플로우, 그리고 사용자가 실제로 한 번 클릭해 준 codegen 녹화.

녹화가 못 잡는 4가지 — 반드시 프로브로 실측
  1. 캔버스 그리드 셀 입력 — 좌표만 남아 재현 불가(그리드 API 필요).
  2. 성공 판정 신호 — 저장/적용이 실제로 됐는지는 녹화에 없다. 이 판정이 없으면 팬텀 성공이 난다.
  3. 타이밍·재시도 규율 — 사람이 기다린 시간은 기록되지 않는다.
  4. 리스트/그리드 행 구조 — 클릭 한 번은 잡히지만 행 셀렉터·컬럼 매핑은 별도 덤프가 필요하다.

for attempt in 1..3:

    스텝마다 스크린샷 + 그리드/DOM JSON 덤프 저장

    실패? → 원인 분류 → 변경 "1개만" 적용 → 변경 이력 기록
상한 초과 → 실패 증거 + 분류 + 시도 이력을 묶어 도메인 전문가에게 에스컬레이션
  • 한 시도에 가설 하나만 바꾼다(셀렉터 하나, 좌표 하나, 대기 방식 하나). 여러 개를 동시에 바꾸면 무엇이 고쳤는지 모른다.
  • 원인 분류가 곧 다음 수정 방향이다 — 셀렉터 드리프트 / 타이밍 / 필드 부재(문서종류 편차) / 트리거 미발화(setValue) / 숨은 백킹필드 / 피커 미적용 / 좌표(뷰포트) / 권한 / 데이터 없음(업무 전제 — 자동화 버그가 아닐 수 있다) / 팬텀 저장 / 코드·명칭 레벨 불일치(사용자가 준 코드는 실측 매핑 전까지 가설).
  • 스크린샷 every step — 헤드리스는 사용자가 못 본다. 스텝별 PNG로 스토리보드를 만들면 도메인 전문가가 즉시 원인을 짚는다. 과거 다회의 막힌 조사를 이걸로 뚫었다.
  • 에스컬레이션 규칙 — 라이브 2~3회 실패하면 멈춘다. 실제 화면 동작(어느 팝업이 뜨는지, 어떤 수동 제스처가 먹는지, 그 필드가 애초에 있는지)은 브루트포스보다 손으로 하는 사람에게 묻는 게 빠르다. 사용자 힌트 두 개("행을 선택하라", "금액은 확인이 필요하다")가 각각 수 시간의 벽을 뚫었다.

8.4 e2e 사이클 — "저장 없는 반복은 무의미"

한 사이클 = 작성 → 영속 검증 → 삭제(F6) → 잔존 0 확인. 왜 실저장까지 하는가:

  1. 저장 게이트를 닫고 도는 반복은 팬텀 성공을 잡지 못한다 — 코드는 "완료"인데 ERP엔 아무것도 없는 상태가 실제로 발생했다.
  2. 파생값 정합(계산 필드가 저장된 문서에 기대값으로 들어갔는지)은 재조회로만 확인된다. 유닛테스트 통과 ≠ 실 저장값 정합.
  3. 삭제까지 검증해야 테스트 데이터가 실운영에 남지 않는다.
  • cycle 1 안전 게이트 — 첫 사이클이 PASS가 아니면 나머지를 돌리지 않는다(회귀 상태에서 전표 양산 방지).
  • 최종 검증은 10회 실저장 사이클. 사이클마다 입력값을 흔들어(.5 반올림 경계 포함) 파생 로직까지 검증한다 — 비가역 저장에서는 반올림 방식(ROUND_HALF_UP vs 파이썬 내장 round의 은행가 반올림) 1원 오차도 영구 확정된다.
  • 단계별 소요를 리포트로 남기면 다음 최적화 대상이 바로 보인다(예: 총 168s 중 문서 반영 82s).
  • 제품 경로로 테스트한다 — 그래프를 직접 호출하지 않고, 실제 프론트 폼을 위젯으로 조작해 실행한다. 그래야 폼→서버 파라미터 주입→러너→기록까지 전체가 검증된다.
함정 — 하네스도 부패한다

파라미터 계약이 두 번 바뀌는 동안 e2e 하네스가 따라가지 못해 3주간 로그인 전 즉시 실패했고 아무도 몰랐다(2026-08-01). 계약 변경 시 e2e 하네스 동반 갱신을 릴리스 체크리스트에 넣어라. 또 e2e는 독립 실행이라 logging.basicConfig가 없으면 INFO 진단이 통째로 유실된다.

8.5 게이트 프로브 — 회귀를 정량으로 증명한다

간헐 실패(24.8%)를 고친 뒤 "고쳐졌다"를 어떻게 증명하나? 프로덕션 코드를 100% 그대로 재사용하는 순수 계측 프로브를 만들어 전/후 실패율을 비교했다 — 매 회 새 컨텍스트+로그인(공지 팝업 레이스까지 재현), 프로덕션과 동일한 배율, 실패 런과 동일한 파라미터. 결과: 수정 전 20회 중 1실패 → 수정 후 20/20. 수치가 아니면 "고친 것 같다"에서 벗어날 수 없다.

8.6 운영 — 셀렉터 드리프트 런북

ERP 업데이트로 셀렉터가 바뀌는 것은 언제냐의 문제다. 대응이 5분이냐 반나절이냐는 §1.1의 단일 소스 구조가 가른다: ① 라이브 1회로 실패 스텝·아티팩트 확보 → ② 원인 분류로 어느 단일 소스 파일인지 특정 → ③ DOM/getColumns() 덤프로 실제 값 확인 → 1파일만 수정 → ④ 프로브로 그 스텝만 재확인 → 사이클 재실행 → ⑤ 명세의 검증 로그 갱신, 커밋.

8.7 서브에이전트/자동 리포트 검증 — 디스크가 심판이다

탐색·다회 프로브를 AI 서브에이전트에 위임해 본 경험에서 나온 규칙. 실제로 한 서브에이전트 포크가 하지 않은 작업을 완료로 조작 보고한 사건이 있었다(2026-08-19) — 존재하지 않는 전표번호와 스크린샷 3종을 인용했고, 모순 보고를 받고 디스크 아티팩트를 대조해 적발했다. 이후 규칙:

  • "실측/완료" 주장은 아티팩트(파일 존재·내용·mtime) 대조 후에만 영구 문서에 승격.
  • 프로브 지시에 "보고에 아티팩트 파일명 필수" 조항.
  • 모순된 보고 2건이 오면 즉시 디스크가 심판 — 대화 기록이 아니라 파일시스템을 믿는다.
  • 승격 후 뒤집히면 "조작 보고로 확인돼 정정" 이력을 남긴다. 조용한 수정 금지.

9. HTTP API 폴백 — 브라우저 없이 읽기

브라우저 자동화의 대전제("모든 상호작용은 브라우저로")에도 예외를 명문화할 가치가 있는 자리가 있습니다 — 읽기 전용 대량 조회.

마스터 코드 카탈로그(예산단위·프로젝트·거래처 수천 건) 동기화는 브라우저 코드피커 페이징으로 하던 것을, SPA가 실제로 쏘는 HTTP를 관찰·재현해 브라우저 없는 직접 호출로 전환했다(2026-08-28, 읽기 전용에 한해 사용자 승인). 실측으로 확정된 사실들:

  • 로그인은 form-urlencoded POST 한 번 → JWT 취득. 쿠키 워밍 불필요.
  • 이후 모든 조회는 커스텀 헤더(x-authenticate-token) 하나면 된다 — 쿠키도, 사용자유형 전환도, 메뉴 진입도 불필요. 브라우저에서 수십 초 걸리던 진입 의식이 API에선 존재하지 않았다.
  • UI의 페이지 크기 500은 클라이언트 값일 뿐, 서버는 5,000도 받는다.
함정 — 파라미터가 실제 필터다

예산단위 조회의 dept_cd는 형식 파라미터가 아니라 실제 권한 스코프 필터였다. 부서 A로 조회하면 2,282건, 부서 B로 조회하면 2,943건이고 A는 B의 완전 부분집합 — 즉 "전사 전량"이 아니라 로그인 사용자 부서의 스코프다. 흥미롭게도 기존 브라우저 경로도 같은 편향에 노출돼 있었다(ERP가 서버에서 같은 필터를 걸고 있었으므로). API 전환이 숨은 편향을 드러낸 셈. 완전성이 필요하면 넓은 스코프 계정을 쓰거나 여러 부서의 합집합으로 조회해야 한다.

  • 폴백 설계: API 우선 → 실패/킬스위치 시 기존 브라우저 경로로 폴백. upsert에 stale 보호를 넣어 나쁜 API 응답이 기존 데이터를 파괴하지 못하게 한다. 쓰기/상신은 여전히 브라우저 전용.
  • 완전 browserless가 불가능한 자리도 있다 — 조직도 API는 별도 포탈 소속이라 브라우저 위젯이 계산하는 서명 헤더가 필요했다(리버싱 불가). 해법은 하이브리드: 브라우저로 화면을 한 번 열어 위젯이 쏜 요청 헤더를 캡처 → 같은 헤더로 page.request 재요청해 전량 트리 수신. 덤으로 기존 DOM 스크레이프의 lazy-load 누락까지 해소됐다.

참고로 이 기법은 진단에도 쓰인다: 프로덕션에서만 나던 로그인 루프를 헤드리스 Playwright로 실 사이트를 재현해 쿠키 domain을 직접 관찰해서 원인(세션 쿠키가 api 도메인 host-only 발급이라 front 도메인에 미전송)을 확정했다(2026-07-10). 브라우저 자동화 도구는 자동화만이 아니라 관찰 도구다.

11. 치트시트 — 원칙 요약

새 화면을 자동화하기 전에 한 번, 간헐 실패를 만났을 때 한 번 훑어보세요.

  1. 추측하지 말고 실측으로 확정한다. 명세의 모든 미확정 값은 ❓로 적고, 프로브 실측 후에만 ✅로 승격한다.
  2. 비가역 액션은 항상 게이트 뒤에. 게이트가 닫힌 채 종단 완주하는 것부터 검증한다. 삭제 경로가 없는 화면은 비가역 동사 직전에서 멈춘다.
  3. 판정은 조건이, 시간은 예산. 성공 판정은 상태 조건(요소·rowcount)이 하고, 시간은 실시간(monotonic) 상한일 뿐이다. 명목 카운터 금지.
  4. 값 주입(setValue)과 타이핑은 다른 행위다. 무언가를 트리거해야 하는 필드는 반드시 실 에디터에 타이핑하고 Tab으로 커밋한다.
  5. 세팅했으면 독립 리더로 재확인한다. 자기충족 readback 금지. 값이 다르면 중단, 읽지 못하면 경고 후 진행(로그 필수).
  6. 검증은 dataSource가 아니라 표시값으로. 코드는 저장됐는데 이름이 안 보이면 숨은 필드다.
  7. 셀렉터는 콘텐츠가 아니라 구조로. 이미지 src·텍스트 라벨 매칭은 깨진다. 클래스·id, 그것도 단일 소스 파일에 모아서.
  8. 좌표는 bbox 동적 계산으로만. 절대 좌표는 뷰포트가 바뀌는 순간 전멸한다. 검증은 프로덕션과 같은 뷰포트·배율로.
  9. 요소가 지금 없음 ≠ 실패. 출현 폴링이 기본값. 단 0건은 조기 안정으로 인정하지 않는다.
  10. 팝업 처리 축을 나눠라. 인페이지 레이어 / 별도 창 / 차단 모달은 다른 메커니즘이다. 업무 창은 확정될 때만 닫는다(fail-safe).
  11. 실패 경로도 정리까지가 책임이다. 안 닫힌 팝업 하나가 다음 왕복을 오염시킨다.
  12. 재시도는 실패 클래스를 가려서. 크래시 1회 복구는 가치, 원인 모를 재시도는 증상 은폐다. 간헐 실패가 재시도로 "해결"되면 진범이 따로 있다.
  13. 한 시도에 가설 하나. 실패 증거(스크린샷·DOM 덤프)를 매 스텝 남기고, 원인을 분류하고, 변경 이력을 적는다.
  14. 2~3회 실패하면 사람에게 묻는다. 실사용자의 한 마디가 수 시간의 브루트포스보다 빠르다. 그래도 안 되면 headed 동반 세션.
  15. 저장 없는 반복은 무의미. e2e는 작성→영속 검증→삭제→잔존 0 사이클로. 첫 사이클이 실패하면 나머지를 돌리지 않는다.
  16. 수치로 증명한다. "고친 것 같다"가 아니라 게이트 프로브 전/후 실패율로. 하네스 자체의 부패도 감시 대상이다.
  17. ERP의 에러는 한 번에 하나씩만 나온다. 반려 처리 루프는 "문구 확인 → 해당 필드 해결 → 재시도"여야 한다.
  18. 인덱스 공간을 확인하라. off-by-one(end-inclusive), 데이터 행 vs 아이템 인덱스, 1-기반 트리 — API마다 세는 방식이 다르다.
  19. 읽기 대량 조회는 HTTP 폴백을 검토하라. 단 파라미터가 실제 필터(권한 스코프)일 수 있음을 실측하고, 쓰기는 브라우저 전용으로 남긴다.
  20. 자동 보고는 디스크로 검증한다. 완료 주장은 아티팩트 대조 후에만 믿는다 — 사람이든 AI든.
