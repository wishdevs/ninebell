# 외상매출금 전표 결재 — 프로세스 정의 (voucher-receivable)

> 회계전표 그룹 에이전트. **결의서입력(GLDDOC00300)이 아니라** 총계정원장 > 전표관리 >
> **전표조회승인** 화면을 다룬다(신규 화면·신규 아키타입 — 문서 생성이 아니라 조회+결재).
> 상태: **v1 — 헤드리스 라이브 프로브 완료(2026-07-20), 배치(3건) 라이브 스모크 그린(2026-07-21).
> 진입·조회 8필드·결과그리드·결제창(별도 팝업 Page)·취소 비영속·배치순회(D7) ✅.
> 미해소: EAP draft 잔존·보관버튼 동작(❓).**
> 형제(같은 화면, 전표유형만 다름 — 향후): 외상매입금(`voucher-trade-payable`),
> 미지급금 법인카드(`voucher-card-payable`).

## 개요

전표조회승인 화면에서 **미결·전자결재저장 상태의 매출전표(국내/해외)**를 조회한 뒤,
목록을 한 건씩 돌며 **결제(결재) 창을 열어 전자결재로 실제 상신**한다(정책 변경
2026-08-07 — 종전 "가상 상신 로그만"에서 개방). 상신은 `loop_approvals` 의
**`allow_submit` 게이트** 뒤에 있고 기본값은 False(=가상 상신 로그만)이며, 회계전표
3종 그래프 빌더가 True 로 연다.

- 입력 방식: 실행 전 폼(조회 조건은 대부분 고정, 회계일만 월 선택). HITL 개입 없음(무개입 완주).
- 완주 조건: 조회된 전 건에 대해 (선택→결제창 열기→상신 클릭→자식창 닫힘 확인) 루프 완료.
- **FI 전표는 불변**: F7 저장·F6 삭제는 이 화면에 없다. 결제창에서 하는 일은 상신 하나이고,
  상신된 전자결재 문서는 EAP 에서 되돌릴 수 있다(아래 안전 섹션).

## ⚠ 비가역 / 안전

- **실제 상신(전자결재 상신) 실행 — 사용자 승인 2026-08-07.** 결제창(EAP) 상단 우측
  **상신**(파란 체크, ~922,30)을 실제로 클릭한다. 클릭 주체는 `steps.click_child_submit`:
  **fresh 좌표 재평가 → 클릭 → 확인 다이얼로그 best-effort 처리 → 자식창 닫힘 = 성공 판정**.
  실패하면 다음 행으로 넘어가지 않고 **런을 하드 중단**한다.
  - **가역 근거**: 상신문서 결재취소 → 미결문서 상신취소 → 임시보관문서 삭제까지
    `e2e/eap_approval_cancel_probe.py`(2026-08-07 신규, 2회 실검증 PASS)로 회수된다.
    비가역이 아니게 되었다는 것이 정책 개방의 유일한 근거다.
  - ❓ **상신 후속 다이얼로그·성공 신호는 미실측**이다. 확인 다이얼로그를 best-effort 로
    두고 **창닫힘**을 성공 판정으로 삼은 이유이며, 첫 라이브 실행에서 실제 문구·전이를 확정한다.
  - `allow_submit=False`(기본)이면 종전대로 가상 상신 로그만 남기고 닫는다.
- ⚠ **상신 후 행 소멸 → 재조회·인덱스 재매핑(사용자 리포트 2026-08-07)**: 실상신된 전표는
  조회 필터(**미결·전자결재저장**)를 벗어나 **결과 그리드에서 사라진다**. 초기 그리드 기준으로
  잡아 둔 인덱스가 그만큼 앞으로 당겨지므로, 가상 상신 시절의 "인덱스 고정" 가정이 깨진다
  (가상 상신은 행이 남아 문제가 없었다). 규율은 **D7 의 확장**으로 다룬다 — 아래 D7-3.
- **D7-3 상신 반영(allow_submit 전용)**: 그룹/건 **상신 성공마다 재조회(F2, `steps.run_query`)**
  로 그리드를 확정 상태로 만든다(마지막 그룹/건은 생략 — 뒤에 쓸 대상이 없다). 이후 대상
  인덱스는 **"이미 상신된 앞 행 수"만큼 차감**해 재매핑하고, **키를 아는 대상**(배치 그룹의
  `docu_nos`·카드의 선계획 키)은 **체크 직전 행 키(DOCU_NO) 대조**로 확정 검증한다.
  - 키 **불일치 = 하드 중단**("상신 반영 후 행 재확인 실패 — 예상/실제"). 키를 **못 읽으면**
    모호로 보고 대조를 생략한다(기존 D7 규율과 동일 — 리더 오탐으로 런을 끊지 않는다).
  - 재조회 후 **잔여 행수**는 기대값(직전 잔여 − 이번 상신 건수)과 대조하되 **soft(warn)**.
    잔여가 어긋나도 다음 대상은 키 대조로 확정하므로 여기서 끊지 않는다.
  - 게이트가 닫힌 경로(가상 상신)는 행이 남으므로 **재조회·재매핑을 하지 않는다**(종전 동작).
  - 구현: `nodes/approvals.py`·`nodes/approvals_batch.py`(`submitted_original` 누적·
    `remaining_expected`·`_row_key`). 회귀 테스트 4건 추가.
- **상신 개방은 이 계열(전표조회승인 3종) 한정이다.** 결의서입력 계열(card_collect·trip_* 등)
  다른 에이전트는 **상신 금지 그대로**다.
- **보관 버튼(~860,30)은 여전히 누르지 않는다** — 실제 저장/제출 여부 미확정(❓). 안전하게 미클릭 유지.
- 결제창 열기→닫기(`close()`)는 FI 전표에 **비영속 확정 ✅**(프로브 3회: DOCU_NO=FI2026070100000010
  이 미결/저장 불변). 이 화면엔 F7 저장·F6 삭제 자체가 없다.
- ⚠ **EAP draft 잔존 이슈(미해소)**: 결제창을 **여는 것만으로** 전자결재(EAP, `uc.ninebell.co.kr`)
  시스템에 새 임시문서(docID 1013899→1013905→1013906 매 오픈 증가)가 생기는 것으로 관찰됨. FI
  전표는 불변이나 EAP 임시/진행문서함에 draft 가 쌓일 수 있다. **배치 순회 전 도메인 담당자
  확인 필요** — 문제면 (a) 순회 안 함, (b) 열지 않고 목록만, (c) EAP draft 정리 로직 추가 중 택일.
  ❓ **상신을 실제로 실행하면 이 draft 가 상신문서로 넘어가 잔존이 줄어드는지는 미확정**이다
  (상신 개방 전 관측이라 재측정 필요). 회수 수단은 `e2e/eap_approval_cancel_probe.py` 가 있다.
- 테스트는 격리 계정(이트라이브2/1111)에서만.
- ⚠ **처리 범위: 전체 진행(사용자 결정 2026-07-21)** — max_rows 게이트/`allow_batch` 제거, 기본이
  조회된 **전 건 순회**다(params.max_rows=None). 즉 한 실행이 대상 건수만큼 결제창을 연다
  (예 31건이면 31회). **2026-08-07 부터는 그 전 건이 실제 상신된다** — 회수는 EAP 결재취소
  프로브로 한다. EAP draft 잔존 처리(위 이슈)는 담당자 확인 대기 상태로 남는다 — 노출·실행은
  사용자 지시로 열려 있다.

## 신규 프론트 요구 — 라이브뷰 부모/자식 창 탭

라이브 브라우저 화면 **우측 상단**에 부모창/자식창을 나타내는 **탭(버튼)**을 두고 번갈아 볼 수
있게 한다. **결제창이 뜨면(결제 진행 중) 자식창 탭을 자동 활성화**해 결제창을 보여준다.
자식창이 닫히면 부모창으로 복귀(활성 탭 원복).

### 라이브 프레임 아키텍처 실측(탐색 2026-07-20)
현재 파이프라인은 **단일 페이지** 캡처다 — `app/live/runner.py`가 헤드리스 Chromium 페이지 1개를
열고, `app/live/screencast.py:screencast_pump(page, events)`가 그 페이지에 CDP 세션 1개를 바인딩.
프레임은 `{"screenshot": "data:image/jpeg;base64,..."}`(events.py)로 **창 식별자 없음**. 기존
"팝업"은 전부 같은 페이지의 Kendo `.k-window` DOM 오버레이(이미 스크린샷에 포함). **실제 새
브라우저 창(window.open→별도 Playwright Page)을 다루는 코드는 전무**(`context.on("page")` 0건).

→ 결제창이 **(B) 진짜 새 창**이면(사용자 표현 "새 시스템 윈도우" = 유력) 신규 플러밍 필요:
1. `runner.py`: `context.on("page")`로 새 페이지 감지 + 페이지별 `screencast_pump` 기동(창 role/id 태깅).
2. 프레임 프로토콜: `{"screenshot", "window": "parent"|"child", "windowId"}` 키 추가
   (`app/live/events.py`, `nbkit/patterns/__init__.py:emit_shot`, `src/lib/live/types.ts`).
3. `app/live/session.py`: `latest_shot` 단일 슬롯 → 창별 맵(부모/자식 덮어쓰기 방지).
4. 프론트 `use-live-run.ts` 리듀서: `screenshot` 단일값 → `{parent, child}` + `activeWindow`
   (자식 프레임 첫 등장 시 자동 전환).
5. 프론트 `live-browser-stage.tsx`: 브라우저 크롬바(우측 상단 StatusBadge 옆)에 탭 토글 추가.
→ 결제창이 **(A) `.k-window` 모달**이면 캡처 변경 불필요, `{"window": ...}` 신호만 추가하면 됨.
**A/B 판정은 프로버 결과로 확정**(❓).

## 배치 결재(외상매출금 전용, 사용자 요구 2026-07-27)

기존 "한 건씩 결제 올리기"를 **하위(계정정보) 건수 기반 묶음 결재**로 바꿨다.

### 규칙(사용자 확정)
1. 조회로 **전체 대상 건수**를 파악한다.
2. 각 전표의 **하위 그리드 건수**를 파악한다.
3. 하위 건수가 **단독 200 이상**인 전표는 **먼저 단독 결재**.
4. 나머지는 **합계가 200이 안 되도록**(< 200) 묶어 **일괄 결재**.

### 실측 근거(2026-07-27, 읽기전용 프로브 2종)
| 확인 | 결과 |
|---|---|
| 마스터 그리드에 하위 건수 컬럼 | **없음**(27컬럼 전수 확인) → 행별로 읽어야 함 |
| 하위 로딩 트리거 | `setCurrent` 만으로 재조회됨(checkRow 불필요) — 138행 전부 **개별 갱신 확인**(디테일 지문 138개 상이) |
| 행당 비용 | 평균 **372ms**(min 160·max 391) → 138건 전수 **52초** |
| 실제 분포 | 하위 **3~17건**(137건이 3~9, 1건만 10~49) · 합계 436 · **200 이상 0건** |
| 다중 선택 결재 | 2행 체크 → 결재 1회 → **자식창 1개**에 **두 전표번호 모두** 표시 = 묶음 성립 |
| 배치 라이브 | 5건 → **결재 1회**, D7 2종 모두 ✅(스모크 ALL PASS) |

→ 현재 데이터 기준 138건이 **3묶음**으로 처리된다(결재 138회 → 3회).
아티팩트: `e2e/artifacts/voucher_receivable_detail_counts.json`,
`e2e/artifacts/voucher_receivable_batch_approval.json`.

### 구현
- `batching.py` — `plan_approval_groups()`(순수): 단독(200↑·건수미상) **먼저**, 그 뒤 조회 순서
  그대로 순차 그리디로 합계 < 200 묶음. **정렬 재배치 없음**(로그·화면 대조 용이).
- `steps.read_detail_count()` — setCurrent 후, 디테일 첫 행의 `DOCU_NO` 가 **그 전표와 같아질
  때까지** 확인 커널로 대기한 뒤 건수를 채택한다. ⚠ 대부분 전표가 3라인이라 **건수만으로는
  스테일(이전 행 디테일)을 구분할 수 없다** — 소유 확인이 유일한 근거다. 확인 실패 시 건수
  미상(-1)으로 두고 그 행은 **단독 그룹**으로 뺀다(모르면 안전한 쪽).
- `nodes/count_details.py` — run_query 뒤에 삽입, `approval_plan` 산출(진행률 노출).
- `nodes/approvals_batch.py` — 그룹마다 전체 해제 → 대상 행 일괄 체크 → 결재 1회.

### 적용 범위
**외상매출금만.** 외상매입금은 건별 순회 유지(그래프에 `count_details` 노드 없음), 미지급금
법인카드는 결제창마다 **행별 참조문서**를 다뤄 묶음과 양립하지 않으므로 제외
(`build_voucher_graph(batch_limit=...)` 로 매출금에서만 켠다).

건별 대비 **임시문서가 오히려 줄어든다**.
